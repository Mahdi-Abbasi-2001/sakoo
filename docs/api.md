# Web API

Start: `liara-agent serve` (default 127.0.0.1:8000). All paths are under `/api`. JSON in and out unless noted.
Errors are `{"detail": {"code", "message", ...}}`; localize by `code` (see `docs/message-codes.md`).

## Conventions
- **Auth:** an `HttpOnly` cookie named `session`, set by register/login. Browser code must send credentials (`fetch(..., {credentials: "include"})`).
- **CSRF:** every POST/PUT/DELETE must come from an allowed origin (`WEB_ALLOWED_ORIGINS`, default `http://localhost:3000`) **or** carry `X-Requested-With: XMLHttpRequest`.
- **Isolation:** every object belongs to one user. Other users' objects answer `404 not_found`.
- **Response schemas:** every JSON endpoint has a response model in `docs/openapi.json` (regenerate with `scripts/export_openapi.py`), so client types can be generated from it.
- **Events:** `{id, ts, kind, data}`, ids increase from 1 per run. Kinds and payloads: `docs/design-brief.md` section 6.

## Connecting a Liara account
1. `POST /liara/check` `{token, team_id?}` validates **without saving**: `{valid, teams[{id,name}], team_required, networks[], apps[], code, params}`. `networks` is a list of network **names** (strings) and `apps` a list of existing app **ids** (strings). If `team_required`, ask the user to choose a team and check again with `team_id`. When `valid` is false, `code` says why: `liara_token_invalid` (`params.status` 401), `liara_forbidden` (403), `liara_rejected` (another status) or `liara_unreachable` (no answer from Liara).
2. `PUT /settings` `{liara_token?, team_id?, team_name?, language?}` saves. `team_name` is display-only (take it from the check response); it is kept when other fields change and cleared when the team changes without a new name. The token is encrypted at rest and **never returned**. `language` is `en` or `fa` and also sets the language of the AI's notes and questions.
3. `GET /settings` -> `{has_liara_token, team_id, team_name, language}`; `DELETE /settings/liara-token`; `GET /liara/networks` -> `{networks[]}`.

## Projects
| method, path | body | result |
|---|---|---|
| `POST /projects` | multipart: `name`, and either `file` (a .zip) or `git_url` (public https repo on an allowed host) | 201 `{id, name}` |
| `GET /projects` | | `{projects[]}`, each row: `{id, name, source_kind, git_url, created_at, last_run, live}` (see below) |
| `GET /projects/{id}` | | the same row plus `runs[]` (full history, newest first) |
| `GET /limits` | | `{max_upload_mb, max_extracted_mb, max_files, git_hosts[], max_concurrent_runs, approval_timeout_seconds, max_heal_attempts}` so the UI can show the numbers before the user hits them |
| `DELETE /projects/{id}?confirm=<name>` | | deletes the project, ALL its runs and everything those runs created on Liara (apps, databases, disks, domains, buckets, mail servers: every run that was not cleaned up yet) and then our copy. `confirm` must be the project's name (422 `confirm_mismatch`). Returns `{ok, deleted{apps, databases, ...}}`. If Liara cannot be cleaned (502 `cleanup_failed` with what was deleted so far, or 400 `no_liara_token`) nothing local is deleted, so it can be tried again; 409 `run_active` while a run is going |

**Project row.** `last_run` is `null` or `{id, mode, status, created_at, finished_at, cleaned_at, result}`. `live` is `null` unless the latest successful real run still exists on Liara (not cleaned up):
`{run_id, urls{app: url}, resources[{kind, id, plan, tier, tier_label, hourly_price}], hourly_incl_vat, monthly_incl_vat, free_address_expires_at}`.
Prices are toman including VAT and reflect priced fixes (e.g. after a move to the silver tier). `free_address_expires_at` is seven days after the first successful deploy (unix seconds), when the free `liara.run` address stops working.
**Run result** (`result` on every run row; also in `summary`): `{ok, stopped, reason_code, reason_params, failed_step, diagnosis_code, created{apps[], databases[], database_ids[]}, urls, dry_run, fixes[{code, kind, params, cost_delta_hourly}], heal_attempts}`. `fixes` lists what the agent changed along the way (for example `resize_tier` to silver), so history can say "fixed automatically"; word each by its fix code. Word the result line from `reason_code` / `diagnosis_code` using `docs/message-codes.md`.
**Error params.** Upload and Git errors carry numbers under `detail.params`: `upload_too_large` {limit_mb}, `too_large` {limit_mb}, `too_many_files` {limit}, `git_host` {host, allowed[]}.
**Name clashes** are caught before the approval: an existing app or database name becomes a blocker note `name_taken` {kind: app or database, name} in `plan_ready`, and nothing is created.

Limits (configurable): upload 50 MB, 200 MB extracted, 5000 files; no symlinks; no path escapes; Git hosts `github.com, gitlab.com, bitbucket.org`.

**Status values:** `running`, `waiting` (an open request needs the user), `succeeded`, `failed`, `cancelled` (the user declined the plan), `interrupted` (the server restarted mid-run).
**Open requests** are events (`{id, ts, kind, data}`) of kind `question`/`confirm_request`/`secret_request` without a response yet. They are derived from the log, so they survive page reloads. The id to answer with is `data.id`. An unanswered request expires after 15 minutes and is declined safely (nothing approved, no secret, conservative answer).
**Expiry.** `question`, `confirm_request` and `secret_request` events carry `data.expires_at` (unix seconds, the server's clock). Count down to it; do not compute from the browser's clock.
**Declining a fix.** A declined fix emits `fix_declined`; the agent tries the next fix it has, and if none is applied the run ends as `failed`: `run_finished` has `ok: false`, `failed_step`, `diagnosis` and `reason_code` (the diagnosis code) and **no `stopped` field** (`stopped` appears only for blocked, cancelled, no_plan and error). Resources created before the failure still exist and bill; `result.created` lists them and the user can clean up.
**Step states.** `step_finished.state` is `READY`, `FAILED`, `UNHEALTHY` or (dry runs) `DRYRUN`; it is absent for database steps. **Prices** are toman including VAT; `monthly_price` is what Liara shows for a month (hourly x 720, rounded to 100 toman).
**Plan links.** `plan_ready.plan.links` lists which resource each app uses and through which variable names (`{from, to, to_kind, env[]}`); values are never exposed.
**Secrets:** a value sent to `respond` for a `secret_request` is registered for masking and never appears in any event or log.

## Limits and safety
- At most 2 active runs per user.
- Uploaded code is never executed on the server: the agent reads files, Liara builds them.
- The server restarts safely: running runs are marked `interrupted`; their logs stay readable.
- Set `WEB_COOKIE_SECURE=true` and `WEB_ALLOWED_ORIGINS` to the real site origin when deploying behind HTTPS. Set `WEB_SECRET_KEY` (otherwise a key file is generated in the data dir).

## WordPress through the API (no console steps)
For a WordPress project the agent asks how to run it and offers, first, Liara's ready-made WordPress (OpenLiteSpeed) installed through the normal API: an app from `registry.c2.liara.ir/one-click-apps/wordpress-openlitespeed`, a MariaDB database and a `data` disk (created before the release that mounts it; `POST /v1/projects/{app}/disks {name, size}`). When the site answers, a temporary FTPS access is made through `POST /v1/projects/{app}/disks/data/ftp`, the project's `wp-content` (themes, plugins, mu-plugins, languages; never `wp-config.php`, `.env`, dumps) is sent over it, and the access is deleted (`DELETE /v1/ftp/{id}`). The database dump is the one step left to the person (phpMyAdmin has no API). Plan field `wordpress` marks this delivery; new `would_send` ops `create_disk` and `create_ftp`. Disks and FTPS accesses are in the journal, so run cleanup removes them. Verified on the real service (2026-10-20, four throwaway runs, all deleted): the whole flow works; the site answers 200 and the uploaded theme file is served from the disk. Learned the hard way: `GET` and `DELETE /v1/projects/{id}/disks...` need the app's INTERNAL id (from `GET /v1/projects`, `_id`), a name answers 500, while `POST` takes the name; the id has to be looked up before the app is deleted; `DELETE /v1/ftp/{fname}` takes the FTPS user name (the `_id` answers 404); the FTPS host came back as `eiger.liara.cloud` and port 2112 worked. Also verified: the Apache variant (`wordpress-new`, small plan, 2026-10-20) and a ready-made app without a database (n8n, `/healthz` answered `ok`), both removed again including their disks. Disks must fit inside the plan's storage (a small plan has 5 GB in all; 1 GB + 5 GB was refused with `not_enough_storage_space`), so the executor shrinks the largest disk to fit (Apache WordPress gets a 4 GB `data` disk). Still unverified: disk price, ownership of uploaded files for plugins that write to disk, whether disks of an app deleted by the first (failed) runs were removed with it.

## Learned on the real service (2026-10-20, throwaway resources, all deleted)
- **Rollback**: both routes work. A release made by this agent is rolled back from its kept source. For any other release, Liara refuses its private-registry image through the `image` parameter and says to deploy a one-line Dockerfile `FROM <image>` as a normal source: that is what the agent does. After a release is READY the old one may still answer for roughly 10 to 30 seconds (READY is not serving, also on redeploys and rollbacks). The release's message is the top-level `message` field (also `tag`); `sourceAvailable` is true for releases made from an uploaded source.
- **Metrics**: `GET /v1/projects/{app}/metrics/cpu|memory?since=<unix seconds>` works: CPU in cores, memory in bytes, values as `[timestamp, "number"]` per instance.
- **Uptime**: the real ping (`monitor.ping`) works against a live `liara.run` address.
- **Object storage keys**: `POST /api/v1/keys` needs `buckets` as plain STRINGS (the spec says objects) and `permissions` as an array of `read`, `list`, `put`, `delete` (`write`, `create`, `upload`, `update`, `download` are refused). `DELETE /api/v1/keys/{key}` takes the ACCESS KEY (the id answers 404), and a bucket with a key assigned cannot be deleted (403). The bucket endpoint that worked is `https://storage.iran.liara.site`; an app wrote, listed, read and deleted an object with the agent-made key.
- **Tier change**: a build over the basic tier's 5 minutes ends `TIMEDOUT`; the agent diagnoses `build_timeout`, asks, recreates the app on the silver tier and the rebuild succeeds (confirmed).
- **Disks**: see the WordPress section; listing and deleting need the app's internal id.
- **CLI**: `liara-agent releases | rollback | redeploy | metrics | explain` work from a project folder deployed by the agent (only apps in its journal are touched).

## Running the platform on the internet
Set `WEB_REGISTRATION_CODE` (an invite code): `POST /auth/register` then needs `invite` in the body (403 `invite_required` otherwise; guesses are rate limited) and `GET /limits` reports `registration_code_required`. Without it anyone who can reach the server can make an account and use the server's model key. The Docker image keeps its data and temporary files on the `/data` disk (`TMPDIR=/data/tmp`), because a Liara app's root filesystem is nearly read-only.

## The assistant (chat)
One conversation per person and project (`project_id` 0 = the general one on the dashboard, which can also start projects from a Git repository or a ready-made Liara app). `GET /api/chat?project_id=` returns `{messages, pending, available}` (`available` is false when the server has no language model). `POST /api/chat/messages {project_id, text}` (at most 4000 characters, 40 per 5 minutes) answers and returns the same view plus `hidden_secret` (true when something in the text looked like a secret and was replaced by `[hidden]` before the model saw it). `POST /api/chat/actions/{id} {project_id, decision: approve|decline, value?, confirm_name?}` decides a proposed change; `DELETE /api/chat?project_id=` clears the conversation.
Messages are `{role: user|assistant, text}`; an assistant message may carry `looked` (names of the read tools it used) and `actions`: cards `{id, tool, status: pending|done|declined|failed, summary, needs_value, value_label, confirm_name, price_delta_hourly, warnings, error, link}`. The agent has READ tools (status, costs, logs, releases, variable names, metrics, domains, plans, last run) that run at once, and CHANGE tools (set/unset variable, resize plan, rollback, redeploy, add domain, start run, delete everything, edit files, deploy edits). Making a project record (`new_project`, `install_ready_made`, `create_project_from_git`) happens at once with no card: it costs nothing and touches nothing on Liara; the agent then calls `start_run` and the person is taken to the run page, which shows the plan and price and asks for approval before anything is created that only run after the person approves the card. A secret value is typed on the card (`value`), used once and never stored or sent to the model; deleting everything needs the project name typed (`confirm_name`). The model never sees variable values, tokens or passwords.

### Build mode (the assistant reads and edits the project's code)
Read tools `list_files`, `read_file` (5000 characters at a time), `search_code`; change tools `edit_files` (each entry `{path, content}`, `{path, replace: [{find, with}]}` or `{path, delete: true}`; the card carries `files` and the unified `diff`), `undo_last_edit`, `deploy_edits`, and in the general chat `new_project` (an empty project to fill). Edits are confined to the project's source folder on this server: no `..`, links, `.git`, dependencies or secret files (`.env`, `*.pem`, `*.key`), at most 30 files and 800 KB per proposal, and code containing a key in a known vendor format or a password inside a URL is refused (read it from an environment variable instead). Edits change only this server's copy (a Git repository is not touched); `deploy_edits` releases that copy on the running app, a normal run uses it too. Nothing written is executed here. `rollback`, `redeploy` and `deploy_edits` run in the background and show up in `GET /projects/{id}/deploys`. `redeploy` and `deploy_edits` are RUNS of `mode: release`: the card's `link` is the run page (`/runs/{id}`), which follows the build line by line and ends with the same result card (a failure says the app keeps its previous release). A release run creates nothing (its `created` is empty), is not counted as the project's last deployment, and can be stopped like any run.

### Live answers (server-sent events)
`POST /api/chat/messages/stream` (same body as `/api/chat/messages`) and `POST /api/chat/actions/{id}/stream` (same body as the decision call) answer as `text/event-stream`. Refusals that happen before the answer starts (rate limit, a decision still pending, no model) are ordinary JSON errors. Events (`data: {json}`): `{type: step}` a new answer begins, `{type: delta, text}` the next piece of its text, `{type: tool, name}` a read tool is being used, `{type: card}` a change was proposed, then exactly one of `{type: done, messages, pending, hidden_secret}` (the saved conversation, as `GET /api/chat` returns it) or `{type: error, code, message}` (the codes of the plain endpoints). The step runs to the end and is saved even if the page disconnects. The plain endpoints still work and wait for the whole answer. An OpenAI-compatible model is asked with `stream: true` (and `stream_options.include_usage`, dropped for providers that refuse it).

`POST /projects/{id}/redeploy` (202 `{status: started, run_id}`; 409 `not_a_git_project`, `deploy_busy`) releases the newest code of the project's repository on the running app in the background (the same settings as the first deploy, nothing new created); its outcome is a row of `GET /projects/{id}/deploys`. Deploying on every push (a webhook or CI files in the person's repository) was tried and removed: the person presses "Release latest code" or asks the assistant instead.

## Private networks
A run no longer needs a `network` in `POST /projects/{id}/runs` (the field stays, optional: the name of an existing network to use). The agent decides while it plans (`deploy/network.py`): a project with a database or more than one app needs one shared private network; a single app with no database needs none. With no network on the account it makes one named `<project>-net` after the person approves the plan (`POST /v1/networks {networkName}` on Liara; free); with some, it asks (question `network_choice`: a new network for this project, recommended, or one of the existing ones). `plan_ready.network` is `{name, new}`, or null when none is needed. Liara's API has no call to delete a network that this agent found, so a network it made is recorded in the run's journal but stays when the project is deleted (an empty network costs nothing).

## Stopping a run
`POST /runs/{id}/cancel` (202 `{ok}`; 409 `run_not_active` when it is not going; 404 for someone else's run) stops a run midway. Every step and every build line is an event, so the worker stops at the next one: waiting questions are released, `run_finished` follows with `stopped: "cancelled"`, `reason_code: "run_cancelled"` and what had already been created. Created things stay (the run page offers "Delete what this run created"); a release already building on Liara finishes there, because Liara has no call to cancel one.
